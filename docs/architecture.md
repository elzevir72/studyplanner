# 아키텍처

## 개요
```
[User Browser]
      │
      ▼
[CloudFront] ── 정적 자산 ──> [S3 (React build)]
      │
      ▼ (API 호출, /api/*)
[API Gateway] ──> [Lambda (Python)] ──> [DynamoDB]
```

- 상시 구동 서버 없음 (완전 serverless). 트래픽이 없을 때 비용 $0에 수렴.
- 10명 규모, 하루 단위 기록이라 Lambda 콜드스타트/동시성 이슈는 실질적으로 없음.

## 그룹 특성
현재 참가 그룹은 **일본어(JLPT) 급수 취득을 목표로 하는 어학 스터디**, 실제 참가 인원은 5명 내외. 참가자별 가용 학습 시간 편차가 크고(직장인 등 상황이 제각각이라 하루 2~6시간대로 다양) 참여도 불규칙적(회식 등으로 특정일 불참 가능). **격주(2주) 주기로 오프라인 모임을 열어 학습 내용을 공유·검토·토론**하는 관행이 이미 있음 — 이 특성들이 목표/달성률 설계와 대시보드 주기 설계에 직접 반영됨(아래 ADR 5, 6 참고).

## 결정 배경 (ADR 요약)

### 1. 프론트엔드: React(TS) + 별도 Python 백엔드
"프론트는 React, 개발 언어는 Python"이라는 초기 요구사항은 그대로는 성립하지 않음(React는 JS/TS 기반).
- Streamlit/Reflex 등 "Python만으로 React 프론트 생성" 옵션은 상시 프로세스(WebSocket 연결)가 필요해 순수 serverless(Lambda) 아키텍처와 궁합이 나쁨.
- → **React(TS) SPA + Python Lambda API**로 확정. 프론트/백엔드 언어는 다르지만, 백엔드 로직(집계, 판정 기준 등)은 전부 Python으로 작성되어 "개발 언어는 Python" 취지를 충족.

### 2. 인증: 사용자 선택 + PIN
정식 로그인 없이 드롭다운으로 사용자를 선택. 완전 무인증은 실수로 타인 기록을 건드릴 위험이 있어, 최소 확인 절차로 4자리 PIN을 둔다. 계정 관리 부담(비밀번호 재설정, 이메일 인증 등)은 만들지 않는다.
- PIN은 DynamoDB에 해시(bcrypt 등)로 저장. 세션은 짧은 TTL의 서명 토큰(JWT) 정도로 충분 — Cognito 등 별도 인증 서비스는 이 규모에 과설계.

### 3. 인프라: Serverless Framework
CDK(Python) 대신 Serverless Framework 선택. Lambda + API Gateway 중심 구성에 특화되어 있고 설정이 간결함.

### 4. 도메인: CloudFront 기본 URL (MVP)
커스텀 도메인은 비용(연 ~$12 + Route53 hosted zone ~$0.5/월)이 발생하므로 MVP에서는 보류. 나중에 도메인을 구매해도 기존 CloudFront distribution에 추가만 하면 되므로 재설계 비용 없음.

### 5. 목표(goal) 설정 및 달성률(%)
그룹 공통 목표 대신 **개인별 자율 목표**를 둔다 — 참가자마다 하루 가용 학습 시간 편차가 크고 참여도 불규칙적이라, 획일적 목표는 의미가 없고 오히려 압박이 될 수 있음.
- `Users.daily_goal`(값+단위, 예: 분)을 사용자가 언제든 스스로 설정/변경.
- 매일 `Entries.amount`를 기록할 때, 그 시점의 `daily_goal`을 `goal_snapshot`으로 함께 저장 — 이후 목표를 바꿔도 과거 기록의 달성률은 소급 변경되지 않음.
- 달성률은 저장하지 않고 `amount`/`goal_snapshot`으로부터 읽기 시점에 계산(단위가 같을 때만 계산, 다르면 null).
- 기존 `goal_achieved: boolean` 필드는 폐기하고 이 방식으로 대체.
- % 지표는 단위 무관(정규화)이므로, 그룹 전체 합산은 여전히 안 하지만 향후 "평균 달성률" 같은 그룹 차원 집계가 가능해질 여지는 있음 — 다만 "무압박" 원칙과의 정합성 검토가 먼저 필요해 현재는 보류(미정).

### 6. 인앱 댓글/리액션 기능 — 범위 제외
참가자들이 **격주로 오프라인 모임을 열어 학습 내용을 공유·검토·토론**하는 관행이 이미 있어, 이 모임이 사실상 "의견 나누기" 기능을 대체함. 따라서 앱에는 댓글/리액션 등 인앱 상호작용 기능을 넣지 않는다. `notes` 필드는 격주 모임의 사전 공유/읽기 자료 역할로 한정.

### 7. 멤버 탈퇴: 삭제 대신 비활성화(`status`)
그룹 규모가 작아(최대 10명) 탈퇴로 인한 데이터량 영향이 미미함. 탈퇴 시 `Users.status`를 `inactive`로 바꿔 대시보드/드롭다운에서 제외하되, 과거 기록은 삭제하지 않고 보존한다. 신규 멤버는 그대로 새 `Users` 항목으로 추가.

### 8. 시즌(Season) 도입
JLPT처럼 특정 회차 시험을 목표로 하는 스터디는 "같은 급수를 여러 회차 재도전"하는 경우가 있어, 데이터를 시즌 단위로 끊어 보는 게 유용함.
- `Seasons` 테이블 신설, `Entries`에 `season_id`를 자동 태깅(작성 시점의 현재 시즌).
- 격주 집계 anchor는 `Config`의 고정값 대신 **현재 시즌의 `start_date`**로 계산 — 시즌 전환 시 격주 주기도 자연스럽게 재설정됨.
- 시즌 전체 통계(`/dashboard/season/{season_id}`)를 별도로 제공.

### 9. 멀티그룹 지원: 스키마 확장이 아닌 별도 배포
다른 어학/자격증 스터디에도 이 도구를 쓸 가능성이 있지만, 지금 스키마에 `group_id`를 끼워 넣는 멀티테넌트 방식은 채택하지 않는다. 대신 **동일 코드베이스를 그룹마다 완전히 별도로 배포**(별도 DynamoDB 테이블 세트/별도 스택)한다.
- 이미 IaC 원칙(`infra/CLAUDE.md`)에 "스테이지 분리 대응 가능" 조항이 있어 같은 메커니즘을 그룹 단위로 재사용하면 됨.
- 그룹 간 데이터가 완전히 격리되어 운영 관리가 단순하고, 서버리스라 그룹 하나 추가해도 비용이 거의 늘지 않음(각 그룹이 각자 프리티어 내).
- 스키마에 `group_id`를 미리 넣어두는 것보다 훨씬 단순하며, 지금 시점엔 "가능성"일 뿐 확정 요구사항이 아니므로 과설계를 피함.

### 10. 리마인더/알림 — 범위 제외
격주 모임에서 서로 진도를 확인할 수 있고 "무압박" 원칙과도 맞아, 이메일/푸시 등 능동적 알림 기능은 만들지 않는다. 대시보드를 스스로 확인하는 수동 방식으로 충분.

### 11. 모바일 우선 반응형 웹
매일 짧게 기록하는 습관형 도구 특성상 모바일 사용 비중이 높을 것으로 예상. 네이티브 앱은 스토어 배포/보안 검토 부담이 커 채택하지 않고, 반응형 웹으로 모바일 사용성을 최우선으로 설계한다.

## 집계 로직 관련 결정
- **주간/격주/월간**: 캘린더 기준. 주간은 ISO 8601(월요일 시작), 월간은 달력월(1일~말일), 격주는 그룹 시작일을 anchor로 한 2주 단위. **격주 뷰가 실제 오프라인 모임 주기와 일치하는 기본/우선 뷰.**
- **미수행자 판정 (MVP)**: 해당 주(월~일)에 기록이 0건인 사용자. 목표 달성 여부 기반 판정은 "목표" 개념이 사람마다 다를 수 있어 MVP에서는 배제 — 데이터가 쌓인 뒤 재검토.
- **타임존**: KST(Asia/Seoul) 고정. 날짜 경계(자정) 판단은 서버(Lambda)에서 KST 기준으로 계산.
- **달성률**: `amount`와 그 시점의 `goal_snapshot`으로 계산(단위 일치 시에만). 목표를 나중에 바꿔도 과거 기록엔 영향 없음(스냅샷 고정).

## 비용 추정
10명, 일 1건 기록 기준 트래픽/데이터량 매우 작음. Lambda 프리티어(월 100만 요청), DynamoDB 프리티어(25GB, 25 WCU/RCU), S3+CloudFront 소규모 트래픽 모두 무료 티어 내 — 실질 운영비 $0~$1/월 예상 (Route53 hosted zone 추가 시 +$0.5/월).
