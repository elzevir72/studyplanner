## 1. achievement.ts / achievement.py drift 해소 방식

현재 Python(`backend/domain/achievement.py:47`)은 `if goal.get("unit") is not None:` 가드가 있어서, 목표에 `unit`이 없는 경우엔 미기록 수단을 0%에 포함시키지 않습니다. TypeScript(`frontend/src/achievement.ts:22-24`)는 이 가드 없이 무조건 0%로 포함시킵니다. 다만 현재 실제 데이터 경로상 `goal.unit`은 항상 필수값이라(백엔드 검증 + 프론트 폼 모두), 이 분기 차이는 지금은 드러나지 않는 잠재 위험입니다.

**Q1-1.** drift를 어떻게 해소할까요?

A) TS 쪽에 Python과 동일한 `unit` 존재 가드를 추가해서 로직을 일치시킨다 (지금처럼 두 언어로 각각 구현된 상태 유지, 값만 맞춤)
B) 애초에 이중 구현을 없애고, 프론트가 백엔드로부터 계산된 달성률만 받아쓰도록 구조를 바꾼다 (더 큰 변경 — API가 이미 계산된 rate를 내려주는 엔드포인트가 없다면 추가 필요)
C) 지금처럼 두되, 최소한 두 구현이 같은 케이스를 검증하는 테스트(예: 같은 fixture를 공유하는 방식)를 추가해 향후 drift를 자동으로 감지하게 한다
X) 기타 (아래 서술)

> 💡 **페르소나별 추천**
> - **PM**: **A + C 병행**을 추천. 지금 이 프로젝트는 5명 내외 그룹용 도구라 B(API 재설계)는 리스크·공수 대비 얻는 게 적음 — 현재 achievement rate가 이미 저장 시점(`goal_snapshot`)에 결정되는 값이라 "화면에 즉시 반영되는 낙관적 표시"를 위해 프론트 로직이 필요한 구조 자체는 유지하는 게 맞음. A로 값을 맞추고 C로 재발을 막는 정도면 이번 릴리즈 범위로 충분.
> - **10년차 개발자**: **A만 지금, C는 다음 기회에**. C(공유 fixture 테스트)는 옳은 방향이지만 지금 이 리포에 프론트 테스트 러너 자체가 없다(Reverse Engineering에서도 확인됨) — 그걸 이번 작업에 얹으면 스코프가 "버그 하나 고치기"에서 "테스트 인프라 구축"으로 커진다. 가드 한 줄 맞추는 A는 5분 작업, C는 최소 반나절. 이번엔 A만 하고 C는 별도 작업으로 분리 제안. B는 지금 규모에서 과설계.
> - **기획자**: **A로 충분, 사용자 입장에서 체감 차이 없음**. 지금 어차피 `unit`은 목표 등록 폼에서 항상 필수라 이 buggy path는 실사용에서 한 번도 발동한 적이 없고 앞으로도 그럴 가능성이 낮음. 다만 "숨어있는 버그"라는 찜찜함을 없애는 선에서 빠르게 맞추고 넘어가는 게 좋겠음. B처럼 구조를 바꾸는 건 사용자가 체감하는 가치가 없는데 리스크만 커서 반대.

[Answer]: A

## 2. 디자인 개선 범위

"투박한 디자인을 버리고 싶다"는 요청의 구체적 범위를 좁히고 싶습니다. 코드/미리보기로 확인한 현재 상태:
- 로그인·관리자 로그인 화면: 데스크탑에서 카드 폭(720px)에 비해 내용(폼 하나)이 작아 여백만 과도하게 남음, 브랜딩 요소(로고/일러스트 등) 전무
- 색상: 파스텔 스카이블루 단일 액센트 + 무채색 텍스트 — 톤 자체는 차분하지만 강조 위계가 약함(버튼/탭/칩이 전부 같은 색조)
- 관리자 화면: `user_id`를 raw text input으로 직접 타이핑(참가자 상태 변경 폼도 동일) — 드롭다운 미사용
- 학습 수단 태그 버튼(`.tag-btn`)이 줄바꿈(wrap) 처리라 개수가 늘면 정렬이 흐트러질 수 있음
- 전반적으로 카드/버튼/폼 요소의 시각적 밀도가 균일해서(모든 섹션이 비슷한 회색 테두리 카드) 정보 위계가 약함

**Q2-1.** 이번에 손댈 범위는 어디까지로 할까요?

A) 톤앤매너(색상 팔레트, 타이포그래피 위계, 여백 리듬)만 다듬고 컴포넌트 구조는 그대로 유지
B) 톤앤매너 + 레이아웃(로그인/관리자 화면 여백 문제, 카드 정보 위계, 버튼 스타일 다양화 등)까지 포함
C) 전면 리디자인(디자인 시스템 새로 정의, 기존 CSS 상당 부분 재작성)
X) 기타 (아래 서술)

> 💡 **페르소나별 추천**
> - **PM**: **B**를 추천. A만으로는 "카드 하나가 화면에 덩그러니 뜬" 문제(로그인/관리자 화면)가 그대로 남아서 사용자가 느끼는 "투박함"이 실제로는 안 고쳐질 가능성이 큼 — 색만 바꾸는 건 체감 효과가 작다. C는 이 프로젝트 규모(참가자 5명, 화면 4개)에 비해 투입 대비 산출이 안 맞음. B 정도가 "실제로 덜 투박해 보이는" 것과 "일주일 안에 끝나는 것" 사이의 현실적 지점.
> - **10년차 개발자**: **B, 단 컴포넌트 리팩터 없이 CSS/마크업 조정 선에서**. 지금 구조(각 페이지가 자기 폼을 직접 렌더링, 공용 CSS 클래스 재사용)는 유지보수성 관점에서 나쁘지 않다 — 굳이 컴포넌트 트리를 새로 짤 이유가 없다. `.login-shell` 같은 유틸 클래스를 AdminPage에도 적용하고, 카드 내부 여백/타이포 위계만 손보는 정도로 B의 실익을 대부분 가져올 수 있다. C(디자인 시스템 도입)는 이후 화면 수가 늘어날 때 재고할 문제.
> - **기획자**: **B + 브랜딩 요소 최소 1개 추가**를 추천. 로그인 화면이 "Study Planner"라는 텍스트 제목 하나뿐이라 도구로서의 정체성이 약하다 — 로고까지는 아니어도 파비콘/제목 영역에 작은 포인트(이모지, 심플 아이콘 등) 하나만 있어도 "이 그룹만의 도구" 느낌이 생긴다. 색상 톤 자체(파스텔 스카이블루)는 이미 스터디 그룹 취지(압박감 없는 톤)에 잘 맞으니 유지하는 게 맞고, 문제는 색이 아니라 레이아웃의 여백/균형이라고 봄 — A만으로는 부족.

**Q2-3.** 관리자 화면의 raw text input(`user_id` 직접 타이핑)을 이번에 드롭다운 선택형으로 바꾸는 것도 디자인 개선 범위에 포함할까요? (기능적 개선이지만 화면의 투박함과 직결되는 부분이라 확인합니다)

A) 포함 — 참가자 목록을 불러와 드롭다운으로 선택하게 바꾼다
B) 제외 — 이번엔 시각 스타일만, 입력 방식은 그대로 둔다

> 💡 **페르소나별 추천**
> - **PM**: **A**를 추천. 이건 사실 "디자인"보다 "버그에 가까운 UX 결함"이다 — 관리자가 `user_id`를 정확히 외워서 타이핑해야 하는데 오타 나면 조용히 실패하거나 엉뚱한 사용자가 수정될 위험이 있다(`listUsers()` API가 이미 존재해서 구현 비용도 낮음). 디자인 개선 항목에 묶기보다 "이번 배치에 자연스럽게 포함되는 buglet 수정"으로 취급해도 될 정도로 우선순위가 높다.

[Answer]: A로 했을때 관리자 계정이 노출될 위험은 있지않아?

> **후속 확인 및 최종 결정**: `GET /users`(현재 `listUsers()`가 쓰는 API)는 이미 참가자 로그인 화면에서 인증 없이 공개된 엔드포인트이고 `status="active"` 참가자의 `user_id`/`display_name`만 반환한다 — 관리자 비밀번호/토큰과는 무관해 이 경로 자체에는 노출 위험이 없음을 확인. 다만 별도로 확인한 결과, `listUsers()`는 `active`만 반환해서 관리자가 `inactive` 계정을 다시 `active`로 되돌리려 할 때 드롭다운에 뜨지 않는 실질 문제가 있음이 드러남 → **전체 참가자(active+inactive) 드롭다운**으로 확정. 이를 위해 `require_admin`으로 보호되는 신규 엔드포인트(예: `GET /admin/users`, `users_repo.list_all_users()`는 이미 존재)를 추가하기로 함.
>
> **최종**: Q2-3 = A(포함), 단 `CreateUserForm`은 활성 참가자만으로 충분하므로 기존 `listUsers()`(공개) 사용, `UpdateUserStatusForm`은 신규 관리자 전용 `GET /admin/users`(전체 목록)를 사용해 두 폼 모두 드롭다운으로 전환.

## 3. 기존 구현 기능의 미비점 점검·보완 범위

Reverse Engineering에서 발견된 이슈 중 "UI/기능"과 직접 관련된 항목들입니다 (테스트 부재·CORS·N+1 등 인프라/코드품질성 이슈는 이번 범위에서 제외하고 별도로 다룰지 이후에 판단하는 걸 전제로 합니다).

**Q3-1.** 아래 중 이번에 함께 점검/보완하고 싶은 항목을 모두 골라주세요 (복수 선택 가능).

A) `docs/api.md` 문서와 실제 동작 불일치 수정 (예: `GET /entries/{user_id}` 인가 설명, 시즌 없을 때 400 응답 미문서화, `goal` null 응답 미문서화)
B) 죽은 코드인 `Config` DynamoDB 테이블/`week_start_day` 관련 정의를 인프라·문서에서 정리(제거)
C) `infra/CLAUDE.md`의 Lambda 함수 개수(23→21) 등 사소한 문서 불일치 정정
D) 위 항목들 외에, 실제로 써보면서 느낀 다른 불편함이 있다 (아래에 자유 서술)
E) 이번엔 위 항목 전부 제외 — drift 해소와 디자인 개선에만 집중
