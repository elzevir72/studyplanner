# Code Quality Assessment

## Test Coverage

- **Overall**: Poor-to-Fair, concentrated entirely in one layer. There is no coverage tooling (`coverage.py`, `pytest-cov`) configured anywhere, so this is a structural read of what exists, not a measured percentage.
- **Unit Tests**: `backend/tests/` has 4 files, 19 test cases, and they exercise exactly the 4 modules in `backend/domain/` (`achievement.py`, `dashboard.py`, `dday.py`, `periods.py`) — the pure-function layer the team explicitly designed to be testable. That part is genuinely well covered (edge cases like unit mismatch, zero goal, missing method, empty list are all present).
  - **Zero tests** for `backend/repos/*.py` (5 modules) — acknowledged directly in `backend/CLAUDE.md`: "repos/ 계층에 대한 유닛테스트는 없음(DynamoDB 접근이라 통합테스트 성격 — 현재 미작성)". No `moto`-based or integration test exists either.
  - **Zero tests** for `backend/handlers/*.py` (6 files, 21 endpoint functions) — no test invokes a handler function directly, so the composition logic that lives in handlers (e.g. `entries_handler.put_entry` assembling `goal_snapshot` + `season_id`, or `dashboard_handler.delete_meeting`'s ownership check) is untested. This is exactly the layer where the two most safety-critical checks in the whole app live (write-authorization and meeting-delete-ownership), and neither has a single automated test.
  - No `pytest.ini` / `pyproject.toml` / `setup.cfg` exists, and `pytest` itself is not listed in `backend/requirements.txt`. The tests are written in pytest style (bare `assert`, `test_*` functions) but nothing in the repo pins how they're supposed to be run or by whom — there's no evidence they're run in CI (`.github/workflows/deploy.yml` has no test step at all, so a domain-layer regression would deploy straight to prod).
- **Integration Tests**: None. No tests exercise a real or mocked DynamoDB, no API Gateway event fixtures, no end-to-end smoke test against the deployed stack.
- **Frontend Tests**: **None whatsoever.** No test runner is installed (no Vitest/Jest/RTL in `frontend/package.json`), no `*.test.ts(x)`/`*.spec.ts(x)` file exists anywhere under `frontend/src`. This means the entire UI layer — including `frontend/src/achievement.ts`, which is a hand-maintained parallel reimplementation of backend business logic — has zero automated verification. A regression here would only surface as a visual bug a human happens to notice.

## Code Quality Indicators
- **Linting**: Not configured. No ESLint config (flat or legacy) for the frontend, no `ruff.toml`/`.flake8`/`pyproject.toml` for the backend. `frontend/package.json` has no `lint` script.
- **Code Style**: Reasonably consistent by convention (not tooling) — Python handlers follow a uniform authorize→parse→call-repo→respond shape, TS files use consistent naming. Consistency is a product of a single author working carefully, not of enforced tooling, so it's fragile to drift as the codebase grows or gains contributors.
- **Documentation**: Good at the "why" level — `CLAUDE.md` files at root/backend/frontend/infra and `docs/architecture.md` (14 ADRs) capture design rationale unusually well for a project this size. Docstrings in `backend/domain/*.py` are precise and match the actual algorithm. However, as detailed below, the docs have started to drift from the code they describe, and nothing catches that drift.

## Technical Debt

1. **`docs/api.md` vs actual behavior — several understated/missing details.** Not severe individually, but they compound:
   - `GET /entries/{user_id}` — the docs table marks auth as "필요 (본인만)" but the actual check is `require_participant(event)` only (`backend/handlers/entries_handler.py:10`), with a code comment explicitly saying read access is open to any logged-in participant regardless of whose data it is. The narrative prose elsewhere in `docs/api.md` gets this right ("다른 사람의 user_id로는 조회는 가능"), but the table column is misleading on its own.
   - `PUT /entries/{user_id}/{date}` and `GET /dashboard/meetings` both return `400` when no season is active (`entries_handler.py:47`, `dashboard_handler.py:106`) — this error path is not documented anywhere in `docs/api.md`.
   - `GET /users/{user_id}/goal` returning bare `null` when no goal is set is undocumented in `docs/api.md`.

2. **A commit message that describes the opposite of what its diff does.** `70d32cb` ("[FIX] responses.ok(None)이 null 대신 {}를 반환해 목표 미설정 시 프론트 렌더링이 깨지던 버그 수정") is recorded in the root `CLAUDE.md` progress log as a completed fix. The actual diff (`backend/common/responses.py`) **removes** the substitution that turned `None` into `{}`, restoring the original `null`-emitting behavior — i.e. it's a revert, not a fix, despite the commit message and the CLAUDE.md changelog both describing it as a fix. Current runtime behavior: `GET /users/{user_id}/goal` genuinely returns the string `null` today. This happens to be harmless in practice because the frontend types `getGoal` as `MethodGoal[] | null` and guards with `g ?? []` (`frontend/src/pages/EntryPage.tsx:91`), and `fetch().json()` parses JSON `null` without throwing (so `client.ts`'s `.catch(() => ({}))` never triggers) — but the documentation trail is actively wrong about what the code does, which is a bigger risk than the bug itself: anyone trusting the changelog will misdiagnose a future null-related issue.

3. **`frontend/src/achievement.ts` has a real, if narrow, logic divergence from `backend/domain/achievement.py`.** Both implement "goal exists but no matching study_item → count as 0% in the average," but the Python version gates that on `if goal.get("unit") is not None:` (`backend/domain/achievement.py:47`) before appending 0, while the TS version has no equivalent guard — it unconditionally does `rates.push(0)` whenever `amount` is falsy (`frontend/src/achievement.ts:22-24`). In every currently-reachable code path `goal.unit` is always a non-empty string (both `PUT /users/{user_id}/goal` on the backend and the `EntryPage` goal form require `unit`), so this divergence is dormant — but it is exactly the kind of "two hand-maintained copies of the same rule" risk the task was asked to look for, and nothing (no shared fixture, no test, no lint rule) would catch it if a future goal-creation path ever allowed a null/empty unit.

4. **`Config` table is dead infrastructure.** `serverless.yml` defines a `ConfigTable` (`config_id="GROUP"`, `week_start_day`), grants it full CRUD+Scan IAM permissions, and `docs/data-model.md` documents it — but `grep -r "CONFIG_TABLE\|Config\|week_start_day" backend/` returns zero matches outside `serverless.yml` and the docs. It appears to be a leftover from an earlier design (the docs even say the anchor for biweekly aggregation moved from `Config` to `Seasons.start_date` in ADR 8, which explains why it's now orphaned) but was never removed from infra or `docs/data-model.md`. Low cost (one PAY_PER_REQUEST empty table), but it's unnecessary attack surface and a documentation trap for anyone reading `docs/data-model.md` expecting it to be live.

5. **No retry/backoff logic anywhere against DynamoDB throttling or transient failures.** All `backend/repos/*.py` calls (`get_item`/`put_item`/`update_item`/`query`/`scan`/`transact_write_items`) rely entirely on boto3's default retry behavior (standard retry mode, a handful of retries with jittered backoff) — there is no explicit `Config(retries=...)`, no circuit breaker, no idempotency-key handling for the two-step `activate_season` transaction beyond what `TransactWriteItems` itself guarantees atomically. `backend/common/errors.py`'s `handle_errors` catches "everything else" and turns it into a generic `500`, so a throttling exception surfaces to the user as an opaque "internal server error" with no retry-after guidance. Given PAY_PER_REQUEST billing and ~5 users doing at most a few writes/day, throttling is extremely unlikely to matter in practice — but if it did happen, there is nothing between boto3's defaults and a raw 500.

6. **N+1 query pattern in `meeting_rounds_dashboard`.** `backend/handlers/dashboard_handler.py:112-120` loops over every meeting round and calls `_dashboard_response(...)` per round, and each call independently does `users_repo.list_active_users()` (a `Scan`) plus `entries_repo.list_entries_by_date_range()` (a GSI `Query`). With R rounds registered, this is `2R` DynamoDB calls for one API request instead of fetching users once and entries once and partitioning them by round in memory. At current scale (a handful of meetings/season) this is invisible in cost or latency, but it's a real N+1 that would degrade linearly if the group ran many more meetings.

7. **Full-table `Scan` used for several "small but growing" reads.** `users_repo.list_active_users()`/`list_all_users()`, `seasons_repo.list_seasons()`/`get_current_season()` (scan + `FilterExpression`), and `meetings_repo.list_meetings()` all use `Scan` rather than `Query`. This is explicitly acceptable at the documented scale (≤10 users, a season table with a handful of rows, meetings in the dozens) and the `CLAUDE.md`/`data-model.md` docs are upfront that the design prioritizes "simple access patterns over partitioning" for this reason — so this is not really a bug, but it is a ceiling: `get_current_season()` in particular scans+filters the entire `Seasons` table on nearly every dashboard/entry-write request, and that pattern would need to change well before user count did if seasons ever grew unboundedly (they won't, by design, but it's worth flagging as a scaling assumption baked into the code).

8. **CORS is fully open (`httpApi.cors: true`).** `serverless.yml:21-22` sets bare `cors: true`, which Serverless Framework expands to `Access-Control-Allow-Origin: *` with all methods/headers allowed. Combined with the fact that most GET endpoints require no auth at all (`/users`, `/meetings`, `/dashboard/*`, `/seasons*`) by design ("그룹 내부 전용... URL 자체가 비공개 배포"), this means **any website on the internet can read the group's full study/meeting/dashboard data via a simple fetch from the victim's browser**, as long as they know (or guess) the CloudFront API URL — there's no secret in the URL and no API key. This matches the explicit caveat already written into `docs/api.md`'s "비고" section ("외부 공개 시에는 최소한 그룹 공용 접근키 정도는 추가 검토 필요"), so the team is aware of the tradeoff, but the current CORS setting doesn't even scope allowed origins to the group's own CloudFront domain — a same-origin-only CORS policy would cost nothing and would at least stop casual cross-site scraping by unrelated sites, without requiring a new access-key mechanism.

9. **Authorization matrix is mostly correct and well-reasoned, but two spots deserve a second look:**
   - Meeting delete's "creator-only" rule (`dashboard_handler.delete_meeting`) is correctly implemented server-side (`meeting.get("created_by") != user_id` → 403) and is genuinely tested by inspection to match the documented behavior — but it is **not covered by any automated test**, backend or frontend. The frontend's owner-only delete-button visibility (`DashboardPage.tsx:314`, `round.created_by === session.user_id`) is a UI nicety only; the real enforcement is the backend check, which is correct, but "verified end-to-end" in the sense the task asked about means only manual/production verification exists, not automated.
   - `entries_handler.list_entries` / `get_entry` intentionally allow any authenticated participant to read any other participant's entries (by design, for the "sharing" philosophy). This is consistent with `docs/api.md`'s prose, but combined with finding #8 (no scoping on CORS) and the fact that entry `notes` can contain personal remarks, this means the practical privacy boundary for the whole app is "know the API URL + have any one valid participant token," not "own your own data." That's a reasonable tradeoff for a 5-person trust group and is explicitly the documented intent (`docs/api.md`'s "비고" section), not an oversight — flagged here only because the task asked specifically to check it.

10. **`infra/CLAUDE.md`'s stated "23개 Lambda 함수" is stale/wrong; the actual count is 21.** Counting `functions:` entries in `serverless.yml` gives exactly 21, matching what the root `CLAUDE.md` and `backend/CLAUDE.md` both separately say. This is a minor but real inconsistency between two of the project's own guide documents (`infra/CLAUDE.md` line 18 vs. the other two), suggesting the infra doc wasn't updated at the same time the function count last changed.

11. **The bcrypt/Lambda packaging fragility flagged in `infra/CLAUDE.md` is a live, unresolved risk, not a resolved one.** The workaround (`pip install --platform manylinux2014_x86_64 --only-binary=:all: -t .` in `.github/workflows/deploy.yml:34-39`) is in place and looks correct for the stated problem (bcrypt ships C extensions that must match the Lambda/Amazon Linux ABI), but it's a manual, easy-to-break CI incantation with no test verifying the resulting Lambda package actually imports `bcrypt` successfully before it's deployed — the only signal of failure would be a production `Runtime.ImportModuleError`, exactly the class of failure the project already hit once with the `serverless.yml` location bug. There is no smoke test in CI that invokes even one Lambda handler post-deploy to catch an import-time regression here.

12. **`dashboard_handler.py` has broader responsibility than its name suggests.** It contains all 4 dashboard read endpoints (weekly/monthly/feed/season-agnostic helper) *and* all 5 meeting CRUD endpoints (`list/create/update/delete/meeting_rounds_dashboard`) — 9 of the app's 21 endpoint functions live in one file. This doesn't violate the stated "one handler function = one responsibility" principle (each function is still small and single-purpose), but it does mean the file-level organization implied by the other handler filenames (`entries_handler.py`, `seasons_handler.py`, one concern per file) isn't followed for meetings, which don't get their own `meetings_handler.py` despite having their own `meetings_repo.py`.

## Patterns and Anti-patterns

- **Good Patterns**:
  - **Pure-function domain layer with real, matching unit tests** (`backend/domain/*.py` + `backend/tests/*.py`) — this is the strongest part of the codebase. Date/timezone/aggregation logic, historically bug-prone, is isolated from I/O and actually exercised by tests covering real edge cases (unit mismatch, zero goal, empty list, missing method).
  - **Consistent snapshot-based achievement calculation** — `goal_snapshot` is copied at write time (`entries_handler.py:54`) and achievement rate is always derived, never stored, which correctly upholds the "past records aren't retroactively affected by later goal changes" principle end to end, from `docs/data-model.md` through `entries_repo.put_entry` to `domain/achievement.py`.
  - **The "no group-wide aggregation" principle is genuinely upheld everywhere it matters.** A full read of `backend/domain/dashboard.py`, `backend/domain/achievement.py`, and every handler that surfaces `achievement_rate` confirms there is no function anywhere that sums or averages `amount.value` across different users or across incompatible units — `average_achievement_rate` is explicitly documented and implemented as "one participant's own average over time," and `build_dashboard` always returns a per-participant list, never a collapsed total. This principle is well-enforced in code, not just in docs.
  - **Role-scoped JWT auth is simple and correctly separated** — `require_participant` / `require_participant_self` / `require_admin` in `backend/common/auth.py` cleanly express three distinct trust levels with a single `role` claim, and every handler uses the right one for its risk level (creation/status endpoints use `require_admin`; self-only writes use `require_participant_self`; shared reads and meeting create/update intentionally use the weaker `require_participant`).
  - **Atomic season switch via `TransactWriteItems`** (`seasons_repo.activate_season`) correctly prevents the two-writes-race that would otherwise let two seasons be `is_current=true` simultaneously — a real correctness concern the team identified and handled properly.
  - **KST timezone handling is centralized in one module** (`backend/common/time_utils.py`) and consistently imported rather than each caller doing its own `datetime.now()`/timezone math — this avoids the classic "some code uses UTC, some uses local time" bug class.
  - **Frontend/backend session separation for participant vs. admin** is implemented with genuinely separate localStorage keys and separate JWT scopes, matching the stated requirement that admin and participant login states never interfere with each other in the same browser.
  - **Sensitive field exclusion on API responses** — `admin_handler.create_user` explicitly strips `pin_hash` before returning the created user object (`{k: v for k, v in user.items() if k != "pin_hash"}`), showing deliberate care about not leaking hashes back to the client even though they're already bcrypt-hashed.
