# Integration Test Instructions

## 적용 범위 판단
이 프로젝트는 단일 SPA + 단일 Lambda 백엔드 구조로, "여러 서비스/유닛 간 상호작용"이라는 전통적 의미의 통합 테스트 대상이 없다(마이크로서비스 구조 아님). 대신 실질적으로 의미 있는 통합 지점은 **프론트엔드 컴포넌트와 백엔드 API 계약 간의 정합성**이며, 이는 자동화된 통합 테스트 스위트 대신 이번 배치에서 브라우저 기반 수동 검증으로 확인했다(백엔드가 로컬에 없어 실제 API 응답까지는 검증하지 못했고, 렌더링/상호작용/타입 정합성만 확인 — 아래 "실제 수행한 검증" 참고).

### 정적 검증
- `npx tsc --noEmit` — 프론트엔드 전체 타입 체크, 에러 0건 (Step 3, Step 4 각각 실행)
- `python -m py_compile backend/handlers/admin_handler.py` — 문법 통과
- YAML 파서로 `serverless.yml` 구조 검증 — 신규 라우트(`adminListAllUsers`)와 Config 테이블 제거 3곳 모두 정확히 반영됨을 확인

## 실행하지 않은 것 (제약 사항)
- **실제 API 왕복 검증**: 로컬에 백엔드(Lambda+DynamoDB) 환경이 없어, `GET /api/admin/users`가 실제로 올바른 JSON을 반환하는지는 이번 세션에서 검증하지 못함 — **main 브랜치 배포 후 실제 관리자 로그인으로 재확인 필요** (아래 "다음 확인 필요" 참고)
- **AWS 통합 테스트(moto 등)**: 이 프로젝트에 mocked-AWS 기반 리포지토리 테스트 자체가 없음(기존 상태, Reverse Engineering에서 이미 지적됨) — 이번 배치에서 새로 도입하지 않음(범위 밖)

## 다음 확인 필요 (사용자 승인 하에 배포 후)
1. `main` 브랜치에 배포 후 관리자 로그인 → "참가자 상태 변경" 드롭다운에 실제 참가자 목록(active+inactive)이 채워지는지 확인
2. 드롭다운에서 참가자를 바꿔 선택했을 때 상태 select가 그 참가자의 실제 현재 상태로 바뀌는지 확인 (Q-3=B 동작)
3. `Config` 테이블 제거 후 CloudFormation 스택 업데이트가 무사히 완료되는지 확인 (테이블 삭제는 스택 업데이트 시 리소스 제거를 수반하므로 배포 로그 확인 권장)
