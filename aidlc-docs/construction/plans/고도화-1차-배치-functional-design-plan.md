# Functional Design Plan — 고도화 1차 배치

Application Design에서 이미 컴포넌트 경계·props 시그니처까지 정의했으므로([application-design.md](../../inception/application-design/application-design.md)), 이 Functional Design은 **경량**으로 진행합니다. 신규 도메인 엔티티나 복잡한 백엔드 비즈니스 로직이 없어서(FR-1은 기존 로직에 가드 한 줄 추가, FR-3은 기존 리포지토리 재사용) `business-logic-model.md`/`domain-entities.md`/`business-rules.md`는 최소로 두고, 핵심은 `frontend-components.md`(컴포넌트 상태·상호작용 흐름)에 둡니다.

## Design Plan

- [ ] `business-logic-model.md` — FR-1 drift 해소 로직만 간단히 문서화 (신규 로직 없음, 기존 Python 로직을 TS에 이식하는 것뿐)
- [ ] `domain-entities.md` — 신규 엔티티 없음, `AdminUserSummary`(FR-3) 타입만 기록
- [ ] `business-rules.md` — FR-3의 인가 규칙(누가 무엇을 볼 수 있는가) 정도만
- [ ] `frontend-components.md` — 7개 신규 컴포넌트의 상태/props/상호작용 흐름 상세 (핵심 산출물)

## Context-Appropriate Questions

### Frontend Components — 상태/상호작용 상세

**Q-1.** `TagSelect`(단일 선택 모드)에서, 이미 선택된 태그를 다시 클릭하면 어떻게 동작해야 할까요? 예: "인강"이 선택된 상태에서 "인강"을 다시 클릭.

A) 선택 해제됨(빈 값으로 돌아감) — 다중 선택 모드의 "토글" 동작과 일관되게
B) 아무 반응 없음(단일 선택은 항상 하나를 선택한 상태를 유지, 해제 불가)

> 💡 **페르소나별 추천**
> - **PM**: **B**. 학습 수단은 기록의 필수 항목이라(값이 비면 저장 시 검증 에러) 사용자가 실수로 선택을 지워서 빈 상태로 만들 이유가 없다. 다른 수단을 클릭하면 자연히 바뀌므로 "해제"라는 액션 자체가 불필요.
> - **10년차 개발자**: **B**. 현재 `EntryPage.tsx`의 기존 구현(`updateItem(index, { method: m })`)도 클릭 시 항상 값을 교체할 뿐 "선택 해제" 개념이 없다 — 기존 동작을 그대로 보존하는 게 이번 리팩터(FR-2)의 원칙(NF-1: 기능 변경 없이 프레젠테이션만 재작업)에 맞다.
> - **기획자**: **B**. 사용자가 매일 반복 입력하는 폼에서, 실수로 같은 태그를 두 번 눌러 값이 사라지는 건 오히려 사용성을 해침 — 아무 반응 없는 게 예측 가능하고 안전함.

[Answer]: A

**Q-2.** `Accordion`을 제어형으로 쓰는 `DashboardPage.tsx`의 모임 회차 목록에서, 기존 동작은 "가장 최근 회차만 기본 펼침, 하나를 열면 다른 건 자동으로 닫힘"(아코디언 그룹처럼 동작)입니다. 컴포넌트 설계상 `Accordion` 하나는 자기 자신의 열림 상태만 알 뿐 "형제 아코디언과의 상호배타" 개념이 없는데, 이 상호배타 로직은 어디에 둘까요?

A) `DashboardPage.tsx`가 `openRound` state 하나로 관리하고, 각 `Accordion`에 `open={openRound === r.round}`를 전달 (기존 방식 그대로, `Accordion` 컴포넌트 자체는 상호배타를 모름)
B) 신규 `AccordionGroup` 컴포넌트를 만들어 상호배타 로직을 캡슐화

> 💡 **페르소나별 추천**
> - **PM**: **A**. 기존 `DashboardPage.tsx`(`openRound`/`setOpenRound`)가 이미 정확히 이 방식으로 동작하고 있어서, 그대로 유지하면 리팩터 범위가 늘지 않는다. `AccordionGroup`은 이번 배치 범위(Application Design에서 정의한 7개 컴포넌트)에 없던 신규 컴포넌트라 스코프 확장.
> - **10년차 개발자**: **A**. `Accordion`을 "자기 상태만 아는 단순 컴포넌트"로 설계한 것 자체가 Application Design Q-B의 결정(제어/비제어 겸용, 단 상호배타는 언급 없었음)과 일치 — 상호배타는 페이지가 여러 자식의 상태를 조율하는 문제이므로 부모(`DashboardPage`)가 갖는 게 컴포넌트를 단순하게 유지하는 원칙에 맞다. `AccordionGroup`을 만들면 아코디언이 항상 그룹 안에서만 상호배타로 동작한다는 전제가 생겨 `EntryPage.tsx`의 독립적인 3개 아코디언(각자 열림/닫힘 무관)과 API가 달라지는 불일치가 생김.
> - **기획자**: **A**. 사용자가 보는 동작은 기존과 동일하게 유지되므로 무엇으로 구현하든 상관없지만, 개발자 의견처럼 단순한 쪽이 버그 위험도 적을 것 같음.

[Answer]: A

**Q-3.** 관리자 화면의 `UpdateUserStatusForm`이 드롭다운으로 바뀌면서(FR-3), 참가자를 선택했을 때 `status` select(현재 active/inactive를 고르는 드롭다운)의 초기값을 어떻게 할까요?

A) 선택한 참가자의 **현재 상태의 반대값**으로 자동 설정 (예: active 참가자를 고르면 select가 자동으로 "inactive" — "상태를 바꾸러 왔다"는 의도가 대부분이므로)
B) 선택한 참가자의 **현재 상태와 동일한 값**으로 초기화 (지금처럼 기본값 "inactive" 고정이 아니라 실제 현재 상태를 반영)
C) 현재처럼 참가자 선택과 무관하게 항상 "inactive"부터 시작 (변경 없음)

> 💡 **페르소나별 추천**
> - **PM**: **A**. 관리자가 이 폼을 여는 이유는 거의 항상 "상태를 뒤집으러" 오는 것 — 반대값을 기본으로 채워주면 클릭 한 번(제출)으로 끝나 실수 여지도 준다. 다만 실수 방지를 위해 제출 전 확인 문구("OO님을 inactive로 변경합니다")를 추가하면 더 안전.
> - **10년차 개발자**: **B**를 우선 고려할 만하다 — "현재 상태를 있는 그대로 보여주는 게" 폼의 기본 원칙(select는 서버 상태를 반영해야 함)에 더 맞고, A(반대값 자동)는 관리자가 실수로 제출 버튼만 누르면 의도치 않게 상태가 뒤집히는 위험이 있다. 다만 이 폼엔 이미 확인 다이얼로그가 없어서(다른 관리자 액션들도 마찬가지), A를 하려면 최소한 제출 확인 문구를 함께 넣는 게 안전 — PM 의견에 동의하되 확인 문구는 필수 조건으로 붙이고 싶다.
> - **기획자**: **A + 확인 문구**. 참가자 5명 규모에서 관리자가 이 폼을 쓰는 빈도 자체가 낮고(가끔 있는 탈퇴/복귀), 매번 "무슨 상태였는지 확인 → 반대로 선택"하는 번거로움을 없애주는 게 실사용 편의에 맞음. 확인 문구는 안전장치로 필요.

[Answer]: B

**Q-4.** `Card` 컴포넌트가 `className` prop을 선택적으로 받는데(component-methods.md), 페이지마다 카드 내부 여백/스타일이 조금씩 다를 수 있습니다(예: `today-card`는 강조 배경, `study-item-block`은 일반 배경). 이런 시각적 변형을 `Card` 하나에 variant prop으로 흡수할까요, 아니면 `className`으로 페이지가 직접 오버라이드하게 둘까요?

A) `Card`에 `variant?: 'default' | 'highlight'` 같은 prop을 추가해 강조 카드(오늘 기록 카드 등)를 명시적으로 지원
B) `className`만 열어두고, 강조 스타일은 페이지에서 추가 클래스로 처리 (Card 자체는 최대한 단순하게 유지)

> 💡 **페르소나별 추천**
> - **PM**: **A**. "오늘 기록 카드"처럼 강조가 필요한 경우가 이미 명확히 존재하고(`.today-card`), 이걸 컴포넌트의 정식 옵션으로 노출하면 나중에 비슷한 강조 카드가 또 필요할 때 재사용이 쉽다.
> - **10년차 개발자**: **A**. `className`을 열어두는 방식(B)은 유연하지만, 결국 각 페이지가 `Card`의 내부 스타일을 알아야 오버라이드할 수 있어 캡슐화가 깨진다 — variant prop이 컴포넌트의 "공식 API 표면"을 명확히 하는 더 나은 설계. 다만 variant는 지금 필요한 것만(default/highlight) 최소로 시작.
> - **기획자**: **A**. 디자인 톤 일관성 관점에서도, "강조 카드가 어떻게 생겨야 하는지"를 컴포넌트 레벨에서 한 곳에 정의해두면 나중에 톤을 조정할 때 한 번에 바뀌어서 좋음.

[Answer]: A
